Vehicle Management System

A C++ console application for fleet tracking, rentals, sales, damage inspection, and trip planning.

Live Demo ↗ Source Code

01. The Problem

Renting out a fleet of cars by hand has predictable failure points. Someone forgets to mark a car as returned and it gets double-booked. A late fee gets calculated wrong because nobody wrote down the exact return date. A car comes back with damage and there's no consistent way to decide what that costs the customer. It's just what happens when a business runs on memory and paper instead of a system.

For our university OOP lab project, three teammates and I built that system in C++ ; fleet tracking, rentals, sales, damage inspection, and a customer-facing trip planner, all running as a shared console application.

02. The Approach

We split the project into modules — vehicles and pricing, transactions, saving/loading data, and input safety — and reviewed how the pieces came together as the team built them.

The core architectural decision was using abstract base classes with pure virtual functions so each vehicle type could calculate its own pricing while sharing a common interface. Vehicle, User, and Transaction became the three blueprints everything else built on.

03. What I Built

The system has two kinds of users — Admin and Customer — sharing one fleet. Cars come in four types: Economy, Luxury, SUV, and Van. Every type shares the same basic blueprint but calculates its own price. A few decisions we made on purpose:

  • Renting longer costs less per day. 4–7 days gets a 10% discount; 8 or more gets 20%. Pricing needed its own logic path, not a flat formula.
  • Returns go through an inspection, not just a checkbox. Fuel level, mileage, and condition all get logged. Condition — Good, Fair, or Poor — decides a damage fee (nothing, half a day's rate, or double) that gets added to the final bill automatically.
  • Renting and selling share a backbone but stay distinct. Both are transactions against a vehicle and a customer, but they behave differently enough that treating them identically would have caused problems.
  • Everything saves to disk in plain text files — no database engine. A deliberate scope choice for a four-week lab project: we wanted our time going into the design, not into learning a database.

04. What I Learned

Leading four people through one shared codebase surfaced problems that don't show up when you're building alone — two people writing code against the same shared file at the same time, or one teammate building on top of a piece that hadn't actually been finalized yet. Most of what I'd call "learning" here wasn't really about C++ — it was about sequencing: agree on the shape of the shared pieces before people start building on top of them, or you end up redoing work later. We also hit enough messy console input early on that we gave input-checking its own dedicated piece of the system instead of scattering it everywhere.

05. What I'd Do Differently

Plain text files were the right call for a four-week lab project, but they're the first thing I'd replace — a real database would remove a lot of fragility (one manually broken line can currently mess up loading, though we did build in handling so it skips a bad line instead of crashing). I'd also want real password protection instead of storing login details as plain text, and I'd lock down who owns which part of the system on day one, rather than a few days in, once code already existed that assumed things we hadn't actually agreed on yet.
